- **Extending `Logger` (or any other small DI'd interface) requires a test-stub sweep.** The codebase has ~14 inline `makeLogger()` factories across `tests/{ui,services,infra,lifecycle}/` that all use the *identical* literal `{ info: vi.fn(), warn: vi.fn(), error: vi.fn() }`. When adding a new method (e.g. `debug`), one `sed` over the matched files patches them all in a single pass — no per-file edits needed. Two outliers don't match the pattern: `tests/integration/dropbox-client.pagination.test.ts` (already had `debug` because it was added defensively) and `tests/infra/token-store.test.ts` (uses a `TestLogger` extension type — patch its object literal manually). Search command: `rg -nl 'info:\s*vi\.fn(),\s*warn:\s*vi\.fn(),\s*error:\s*vi\.fn()' tests/`. The same pattern likely applies to other narrow interfaces (`PluginStore`, `VaultAdapter`) the next time a method is added.

- **`tests/fixtures/obsidian-mock.ts` is the only `obsidian` resolution in tests** (`vitest.config.ts` aliases `obsidian → tests/fixtures/obsidian-mock.ts`). When source code adopts a new Obsidian API (`Menu`, `MarkdownRenderChild`, `Notice`, future `Setting`-children, etc.) the mock will NOT have it — production builds fine because esbuild externalises `obsidian`, but the next vitest run blows up with `X is not a constructor` from the test environment. **Rule:** when adding a new `import { X } from 'obsidian'` to any file under `src/`, check whether `X` already exists in `tests/fixtures/obsidian-mock.ts`; if not, add a minimal stub there in the same change. Recently added: `Menu` (with static `_last` for context-menu assertions), `MarkdownRenderChild` (extends Component, takes containerEl). Pattern for new mocks: just enough surface to cover what production calls — additional methods can be filled in lazily when a future test needs them.
- **Code that opens an Obsidian `Modal` reaches `activeDocument.activeElement` in `onOpen()`** — that global is provided by Obsidian's Electron environment and does NOT exist in vitest. Tests that exercise a click path which calls `new ConfirmRestoreModal(...).open()` must `vi.mock('../../src/ui/ConfirmRestoreModal', ...)` with a stub class that captures the constructor opts and no-ops `.open()`. Pattern: stub exposes `static _last = { opts }` so the test asserts the modal received the right payload without needing to walk a real `contentEl`. The Modal's pure render functions (`renderConfirmRestoreContent`, `renderHistoryContent`) ARE testable directly with a recording handle — those don't need this mock workaround. Same pattern applies to any future Modal-opening views.
- **Tests aren't covered by `tsc` — `tsconfig.json` sets `rootDir: "./src"`.** TypeScript diagnostics that fire only inside `tests/**/*.ts` (mock-vs-real type mismatches like `WorkspaceLeaf` mock vs the real type, `HTMLElement`-vs-`MockEl`, unused imports) are noise from `npm run build`'s perspective — they don't block builds and the test harness ignores them. **Rule:** when adding new tests, don't try to "fix" these diagnostics by widening types or casting — the vitest runtime doesn't care. Only fix diagnostics that originate from `src/`. Helps keep test additions surgical.
- **`workspace.on('file-menu')` covers BOTH the file-explorer right-click AND the editor's three-dots more-options menu.** The same event fires for both surfaces — Obsidian distinguishes them via the `source: string` callback parameter (e.g. `'file-explorer-context-menu'` vs `'more-options'` vs `'file-tab-header'`). One `registerEvent(this.app.workspace.on('file-menu', cb))` covers all three contexts; no need for separate `editor-menu` wiring unless the action depends on selection / cursor. **Rule when a user says "right-click on a file/note" in an Obsidian plugin context:** they almost always mean the native file explorer OR the three-dots menu — NOT a custom view's row contextmenu. Reach for `file-menu`, not a per-view `addEventListener('contextmenu', ...)` (`af4edca` was a course-correction commit caused by exactly this misread). Folder vs file filtering: `'extension' in file` works as a duck-typed TFile guard without importing TFile/TFolder.
- **Use `activeDocument`, not `document`, for the active-element / DOM root** — repo's eslint plugin (`obsidianmd/prefer-active-doc`) flags `document.activeElement` and friends as a build error. Reason: Obsidian supports popout windows; each window gets its own document, and `activeDocument` is the window-scoped reference. The lint rule fires AFTER `tsc --noEmit`, which is annoying because a typo passes typecheck and only surfaces in `npm run lint`. **Rule:** when reaching for the document root or the focused element inside a Modal/View, write `activeDocument.activeElement`. The global is provided by Obsidian's runtime, declared in their type definitions, and exists in test mocks too.
- **MockEl is a deliberately thin DOM stub — production code reaching for new DOM methods fails the next test run with `X is not a function`.** Recently added: `removeAttribute` (paired with `setAttribute`), `querySelectorAll` (minimal `.class` / `tag` / `.class tag` selector engine, NOT a full CSS engine — attribute selectors don't work). Component now also has a real `unload()` that propagates to children — needed because `MarkdownRenderChild.unload()` is called on stale-bail paths. **Rule:** when production code starts calling a new DOM method on a `MockEl`-typed element (anything coming out of `createEl`, `contentEl`, view containers), check `tests/fixtures/obsidian-mock.ts` first — extending the mock in the same PR is cheaper than chasing a "X is not a function" error from a test run later.
