# Troubleshooting Memory

<!-- 2026-04-23 -->
- **Splitting a TypeScript super-class into subclasses across a large spec** (e.g., `IntegrityError → ChainError / ConflictError / CorruptionError` during post-review hardening): after the type-definition block is fixed, the old class name lingers in SDD Error-Handling tables, EARS Acceptance Criteria, inline code examples, and per-phase test specifications. Always `grep -nrE 'OldClass\('` across the entire spec tree as a follow-up sweep; don't trust that "the class is redefined" is the whole job. A single find-replace after the split usually closes all 10-15 references in one pass.
- **Phase renumbering across a multi-file plan** (e.g., delete one phase, rename later ones): `git mv` preserves the file content but does NOT rewrite cross-references. Decisions-log rows, PRD→Phase traceability matrices, ADR trade-off notes, and inline prose all accumulate the old numbers. Grep for every retired number (`Phase 11`, `Phase 12`, `T12\.`, `phase-11`, `phase-12`) and fix each individually; 8-10 references per renumbered phase is typical. Keep historical-narrative refs (e.g., "Phase 12 renamed to Phase 10") but disambiguate any claim that references the old number as if still active.

- **Rolldown / native-binding error after switching Docker ↔ host** (`Cannot find module '@rolldown/binding-darwin-arm64'` — but `binding-linux-arm64-gnu` is present): the Docker container's `npm install` materialised only the Linux optional dep into `node_modules/@rolldown/`. On the host (darwin-arm64), `npm install` alone does not re-evaluate optional deps because the lockfile already lists them as resolved. Fix: `rm -rf node_modules/@rolldown node_modules/rolldown && npm install`. The sandbox blocks `/Users/marcus/.npm/_cacache/` writes — the install command needs `dangerouslyDisableSandbox: true`. Lockfile is NOT modified. Applies to any MiYo repo that runs tests both in Docker and on host.

- **Dropbox parameter-less endpoints reject `application/x-www-form-urlencoded`.** `/2/users/get_current_account` (and any `/2/...` endpoint that takes no parameters) returns HTTP 400 *"Bad HTTP 'Content-Type' header"* unless Content-Type is `application/json`, `application/json; charset=utf-8`, `text/plain; charset=dropbox-cors-hack`, or absent entirely. The shared `OAuthConnectFlow.httpPost` helper hardcodes `application/x-www-form-urlencoded` because that's what `/oauth2/token` requires — that helper is NOT reusable for `/2/...` endpoints. New API calls in the OAuth flow must either use `requestUrl` directly (no Content-Type) or send a JSON body with the right header. The form-urlencoded failure is silent in best-effort callers (returns null), so symptoms are downstream — e.g. `dropbox_account_email` permanently empty, settings tab stuck in empty-state.
- **Every async-sourced field on `SettingsContext` MUST be pre-populated at onload before constructing `ArchivistSettingTab`.** `SettingsTab.refreshAsyncFields` (added 2026-04-25 to make the connected-state survive disable/enable) re-renders the entire tab if any of `deviceId`, `deviceDesignated`, `dropboxAccountEmail`, `dropboxUsedBytes` differs from its cached `ctx` value. If the ctx is left at a placeholder default while the real async source returns something else, the FIRST settings-open triggers an "everything-changed" rebuild **mid-typing**, wiping any in-progress text input. Concrete bug: vault_prefix textbox kept appearing empty after entering it twice — see `0c12afd` / `b229281`. When adding a new ctx field with an async getter, also wire its pre-populate in `main.ts` Step 15 next to the deviceId/email block.
- **Obsidian's `TextComponent.onChange` is NOT reliably per-keystroke across versions.** It's wired to the input element's `change` event, which fires on blur — meaning if the user types and then clicks a different sidebar item in the settings dialog (Community plugins, another tab, etc.), the input gets removed from the DOM **before** blur lands, the change event never fires, and the typed value is silently lost. For any "save as you type" text field, attach a direct `'input'` listener on `text.inputEl` in addition to `text.onChange`. See `ef1156a` for the renderText fix that routes both to the same handler. (Note: the original symptom that motivated this fix was actually unrelated — see the silent-validate entry below — but the input-listener wiring is correct hardening regardless.)
- **Silent validation failure looks indistinguishable from "save broken".** `renderText` (and `renderTextarea`, `renderNumber`) wrap `spec.onChange` in a `validate` gate: when validate returns a non-null error string, the handler returns early without calling `spec.onChange`. Without UI feedback, the user sees no error — they assume the save mechanism is broken and start hunting in the wrong place. Concrete: a 4-commit chase (`0c12afd` → `c69e923` → `ef1156a` → `2ccee23`) for "vault_prefix doesn't save" turned out to be the user typing `Test-Vault` with capital letters; the regex `^[a-z0-9][a-z0-9_-]{1,63}$` rejected it and the failure was invisible. Fix in `70ee73a` adds an inline `.archivist-validation-error` div + `mod-warning` border. **Rule:** any new validate-on-input field must surface its error to the user — never silently swallow.
- **Dropbox `files/*` API requires paths to start with `/`; the JS SDK does NOT add it.** All `sdk.filesDownload({ path })`, `filesUpload`, `filesListFolder`, `filesDeleteV2`, and `filesUploadSessionFinish({ commit: { path } })` calls must receive a path that starts with `/`, `id:`, `rev:`, or `ns:` — anything else returns HTTP 400 *"Malformed request"*. Our `src/util/paths.ts` builders return paths app-folder-relative (just `<vault_prefix>/...`); normalisation to `/...` happens at the SDK boundary in `DropboxClient.normalizeApiPath` (`109572e`). Test mocks defined `filesDownload: () => ...` without inspecting the `arg.path`, so 1046 unit tests passed while every live API call was broken — when adding a new files/* SDK invocation, also add a regression test asserting `arg.path` starts with `/`. **Diagnostic shortcut:** when an HTTP 400 surfaces as our generic `PathError("BAD_REQUEST")`, run `scripts/dropbox-inspect.mjs head <prefix>` against the same token; the script uses raw HTTP and surfaces the real Dropbox error message, which is otherwise discarded by `classifyError`.
- **App-Folder OAuth scope auto-prefixes `/Apps/Archivist/` server-side; client paths must NOT include it.** Earlier `src/util/paths.ts` versions used `APP_FOLDER_ROOT = 'Apps/Archivist'` and composed paths like `Apps/Archivist/<prefix>/HEAD.json`. Combined with Dropbox's server-side prefix, files actually landed at `/Apps/Archivist/Apps/Archivist/<prefix>/...` — visible as a double-Apps tree in the web UI (`41e8461`). Builders now return `<vault_prefix>/...` and Dropbox prepends `/Apps/Archivist/` itself. Test mocks accepted any path so 1050 unit tests passed while production data went to the wrong location. **Rule:** for any `app-folder` scoped Dropbox app, treat the OAuth scope as the path root; do not include the app-folder name in any path you send. The diagnostic script `scripts/dropbox-inspect.mjs` uses the same scope and must use the same form. **Recovery from wrong-path data:** after fixing builders, delete the plugin's local `index.json` + `pending_changes.json` so the next backup starts a fresh chain at the corrected path; the orphan folder under the old prefix can be swept via the Dropbox web UI.
