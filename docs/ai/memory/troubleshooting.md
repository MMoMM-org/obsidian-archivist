# Troubleshooting Memory

<!-- 2026-04-23 -->
- **Splitting a TypeScript super-class into subclasses across a large spec** (e.g., `IntegrityError → ChainError / ConflictError / CorruptionError` during post-review hardening): after the type-definition block is fixed, the old class name lingers in SDD Error-Handling tables, EARS Acceptance Criteria, inline code examples, and per-phase test specifications. Always `grep -nrE 'OldClass\('` across the entire spec tree as a follow-up sweep; don't trust that "the class is redefined" is the whole job. A single find-replace after the split usually closes all 10-15 references in one pass.
- **Phase renumbering across a multi-file plan** (e.g., delete one phase, rename later ones): `git mv` preserves the file content but does NOT rewrite cross-references. Decisions-log rows, PRD→Phase traceability matrices, ADR trade-off notes, and inline prose all accumulate the old numbers. Grep for every retired number (`Phase 11`, `Phase 12`, `T12\.`, `phase-11`, `phase-12`) and fix each individually; 8-10 references per renumbered phase is typical. Keep historical-narrative refs (e.g., "Phase 12 renamed to Phase 10") but disambiguate any claim that references the old number as if still active.

- **Dropbox parameter-less endpoints reject `application/x-www-form-urlencoded`.** `/2/users/get_current_account` (and any `/2/...` endpoint that takes no parameters) returns HTTP 400 *"Bad HTTP 'Content-Type' header"* unless Content-Type is `application/json`, `application/json; charset=utf-8`, `text/plain; charset=dropbox-cors-hack`, or absent entirely. The shared `OAuthConnectFlow.httpPost` helper hardcodes `application/x-www-form-urlencoded` because that's what `/oauth2/token` requires — that helper is NOT reusable for `/2/...` endpoints. New API calls in the OAuth flow must either use `requestUrl` directly (no Content-Type) or send a JSON body with the right header. The form-urlencoded failure is silent in best-effort callers (returns null), so symptoms are downstream — e.g. `dropbox_account_email` permanently empty, settings tab stuck in empty-state.
- **Every async-sourced field on `SettingsContext` MUST be pre-populated at onload before constructing `ArchivistSettingTab`.** `SettingsTab.refreshAsyncFields` (added 2026-04-25 to make the connected-state survive disable/enable) re-renders the entire tab if any of `deviceId`, `deviceDesignated`, `dropboxAccountEmail`, `dropboxUsedBytes` differs from its cached `ctx` value. If the ctx is left at a placeholder default while the real async source returns something else, the FIRST settings-open triggers an "everything-changed" rebuild **mid-typing**, wiping any in-progress text input. Concrete bug: vault_prefix textbox kept appearing empty after entering it twice — see `0c12afd` / `b229281`. When adding a new ctx field with an async getter, also wire its pre-populate in `main.ts` Step 15 next to the deviceId/email block.
- **Obsidian's `TextComponent.onChange` is NOT reliably per-keystroke across versions.** It's wired to the input element's `change` event, which fires on blur — meaning if the user types and then clicks a different sidebar item in the settings dialog (Community plugins, another tab, etc.), the input gets removed from the DOM **before** blur lands, the change event never fires, and the typed value is silently lost. For any "save as you type" text field, attach a direct `'input'` listener on `text.inputEl` in addition to `text.onChange`. See `ef1156a` for the renderText fix that routes both to the same handler. (Note: the original symptom that motivated this fix was actually unrelated — see the silent-validate entry below — but the input-listener wiring is correct hardening regardless.)
- **Silent validation failure looks indistinguishable from "save broken".** `renderText` (and `renderTextarea`, `renderNumber`) wrap `spec.onChange` in a `validate` gate: when validate returns a non-null error string, the handler returns early without calling `spec.onChange`. Without UI feedback, the user sees no error — they assume the save mechanism is broken and start hunting in the wrong place. Concrete: a 4-commit chase (`0c12afd` → `c69e923` → `ef1156a` → `2ccee23`) for "vault_prefix doesn't save" turned out to be the user typing `Test-Vault` with capital letters; the regex `^[a-z0-9][a-z0-9_-]{1,63}$` rejected it and the failure was invisible. Fix in `70ee73a` adds an inline `.archivist-validation-error` div + `mod-warning` border. **Rule:** any new validate-on-input field must surface its error to the user — never silently swallow.
- **Dropbox `files/*` API requires paths to start with `/`; the JS SDK does NOT add it.** All `sdk.filesDownload({ path })`, `filesUpload`, `filesListFolder`, `filesDeleteV2`, and `filesUploadSessionFinish({ commit: { path } })` calls must receive a path that starts with `/`, `id:`, `rev:`, or `ns:` — anything else returns HTTP 400 *"Malformed request"*. Our `src/util/paths.ts` builders return paths app-folder-relative (just `<vault_prefix>/...`); normalisation to `/...` happens at the SDK boundary in `DropboxClient.normalizeApiPath` (`109572e`). Test mocks defined `filesDownload: () => ...` without inspecting the `arg.path`, so 1046 unit tests passed while every live API call was broken — when adding a new files/* SDK invocation, also add a regression test asserting `arg.path` starts with `/`. **Diagnostic shortcut:** when an HTTP 400 surfaces as our generic `PathError("BAD_REQUEST")`, run `scripts/dropbox-inspect.mjs head <prefix>` against the same token; the script uses raw HTTP and surfaces the real Dropbox error message, which is otherwise discarded by `classifyError`.
- **App-Folder OAuth scope auto-prefixes `/Apps/Archivist/` server-side; client paths must NOT include it.** Earlier `src/util/paths.ts` versions used `APP_FOLDER_ROOT = 'Apps/Archivist'` and composed paths like `Apps/Archivist/<prefix>/HEAD.json`. Combined with Dropbox's server-side prefix, files actually landed at `/Apps/Archivist/Apps/Archivist/<prefix>/...` — visible as a double-Apps tree in the web UI (`41e8461`). Builders now return `<vault_prefix>/...` and Dropbox prepends `/Apps/Archivist/` itself. Test mocks accepted any path so 1050 unit tests passed while production data went to the wrong location. **Rule:** for any `app-folder` scoped Dropbox app, treat the OAuth scope as the path root; do not include the app-folder name in any path you send. The diagnostic script `scripts/dropbox-inspect.mjs` uses the same scope and must use the same form. **Recovery from wrong-path data:** after fixing builders, delete the plugin's local `index.json` + `pending_changes.json` so the next backup starts a fresh chain at the corrected path; the orphan folder under the old prefix can be swept via the Dropbox web UI.
- **NEVER assign `el.className = ...` on an Obsidian-managed DOM element (ribbon icons, status-bar items, settings rows, etc.).** Obsidian wires layout-critical classes onto these elements (`side-dock-ribbon-action` for ribbon icons, `mod-clickable` for buttons, `setting-item-info` for setting rows). Setting `el.className` REPLACES the entire class list and silently breaks centering / hover / focus styling. Symptom: ribbon icon visually displaced inside its slot (`6e583e1`). **Rule:** always use Obsidian's `addClass(name)` / `removeClass(name)` helpers (or vanilla `classList.add` / `classList.remove`). When a state-tracking handle needs to swap classes per state, remember the classes WE added in a private `appliedClasses` array, then `removeClass` each on the next state change before adding the new ones — leave the rest of the class list untouched.
- **For writes onto tracked TFiles, use `vault.modifyBinary` / `vault.modify`, NOT `adapter.writeBinary` + `adapter.rename`.** The low-level `vault.adapter.*` API bypasses Obsidian's vault tracker — when you `adapter.remove(path)` followed by `adapter.rename(tmp, path)` over an existing TFile, each call returns without error but the on-disk file ends up un-changed AND the in-memory editor keeps showing the original content. Restore-in-place looked broken: `restore_completed` log fired, but file mtime + bytes were unchanged (`e1377cb`). **Rule:** before writing to a path, check `vault.getAbstractFileByPath(path)`; if it's a TFile, call `vault.modifyBinary(file, ab)` (or `vault.modify(file, str)` for text) — that goes through Obsidian's high-level path and atomically updates disk + cache + open editors. Only use `adapter.writeBinary` + `adapter.rename` for first-time writes to paths that aren't yet tracked.
- **`bytes.buffer` on a Uint8Array view exposes the WHOLE backing ArrayBuffer, not just the active range.** When the buffer was created via `subarray()`, slicing, or `new Uint8Array(otherBuf, offset, length)`, `.buffer` returns the full underlying buffer (often much bigger than `byteLength`). Passing that to APIs like `vault.adapter.writeBinary(path, ab)` writes the entire backing buffer to disk, not the slice. **Rule:** when crossing into an ArrayBuffer-typed API, copy into a fresh, exactly-sized buffer: `const ab = new ArrayBuffer(bytes.byteLength); new Uint8Array(ab).set(bytes);`. The cost is one allocation; the alternative is silent data corruption / oversized files.
- **`workspace.getLeaf(false)` does NOT reuse an existing leaf — it always allocates a new one.** The `false` argument only controls whether it splits the current pane; it has no bearing on identity reuse. Symptom: every ribbon click / command-palette invocation of an "open-the-view" handler stacks another tab (`931050e`). **Rule:** for any view that should be open-or-focus rather than open-new-each-time, query `workspace.getLeavesOfType(VIEW_TYPE)` first; if a leaf exists, call `revealLeaf(leaf)` and return; only allocate via `getLeaf(false)` + `setViewState` when nothing matches. Same pattern applies to plugin commands that "show" a registered view.

- **A method that's defined on the FSM but never invoked silently degrades scheduler semantics.** `SchedulerFSM.onVaultEvent()` was implemented to reset the QUIET_WAIT timer on user activity, but no caller ever invoked it — `ChangeDetector.dispatch()` enqueued events into `EventQueue` and stopped there. The FSM still progressed `GRACE → QUIET_WAIT → READY` on its fixed timer, so backups continued to run from the tick loop and nothing looked broken — but "quiet-wait" was effectively "fixed-delay-after-grace," ignoring whether the user was still typing. Fix (`0c00f5e`): `ChangeDetector` exposes `setOnVaultActivity(fn)`; `main.ts` Step 13 wires it to `() => fsm.onVaultEvent()` BEFORE `registerEventHandlers()` runs. **Rule:** when reviewing FSM/scheduler glue, grep every public method for at least one external call site — a method with zero call sites is dead glue, not "well-encapsulated state." For Archivist, the relevant files are `src/main.ts` (the only wiring layer) and `src/services/{ChangeDetector,DeviceCoordinator,SchedulerFSM}.ts`.
- **Backup logging now follows a 2-tier convention — info for user-facing lifecycle, debug for ops detail.** `BackupService` emits `info('Starting full|inc backup')`, `info('full|inc backup done')`, and `info('N files written')` as the user-visible lifecycle (always shown). Per-path "wrote { path }" lines and FSM/cache internals (`fsm_transition`, `manifest_cache_invalidated`) emit at `debug` and only render when `diagnostic_logging=true`. The `debug` gate IS the path-disclosure gate — turning paths on automatically turns operational chatter on. **Rule when adding a new log call inside the backup hot path:** if the user needs to see it during normal backups → `info`; if it's only useful when investigating a regression → `debug`. Don't introduce a third level. Don't surface implementation details (cache, FSM transitions) at `info` — users misread normal events as failures and file bug reports.

- **`workspace.on('layout-ready', cb)` does NOT fire when a plugin is enabled AFTER Obsidian's layout already settled.** The Obsidian `layout-ready` event is a one-shot — once fired, subscribing later just attaches a dead listener. Symptom: `fsm.onLayoutReady()` is never called → FSM hangs in `LOADING` forever → no `GRACE → QUIET_WAIT → READY` chain → only manual `triggerBackupNow` (Cmd+P → "Back up now") works, no auto-inc, no scheduled full. Console looks clean: no `fsm_transition`, no error. **Rule:** for any "do X once layout is ready" wiring, use `this.app.workspace.onLayoutReady(cb)` — the helper fires immediately if already ready, otherwise registers a one-shot. Never `workspace.on('layout-ready', cb)`. Fix in `1143a04`. The lifecycle test "onunload leaves zero lingering workspace listeners" loses its precondition with this change (onLayoutReady doesn't go through `_listeners`); kept as a forward-guard for any future workspace.on usage.
- **In-memory state of a wrapper class (e.g. `EventQueue`) goes stale if a downstream service writes the wrapper's persisted file directly through the underlying store.** `BackupService.advanceQueueCursor` used to call `pluginStore.saveQueue(filteredQueue)` after each commit. The on-disk file was correct (entries pruned, cursor advanced), but `EventQueue.state.entries` in-memory was untouched. Effect: `eventQueue.peekSince(...)` kept returning the just-committed events as "pending" for an entire `inc_interval`, so the FSM tick fired a phantom no-op inc 15 minutes after every real inc — visible in the log as `Starting inc backup` → `Inc backup: no changes` round-trips. Fix (`461f8d6`): added `EventQueue.commitWindow(ts)` that goes through the same opQueue as `enqueue`, mutating in-memory state AND writing to disk atomically. **Rule:** any class that wraps a persisted file must own all writes to it. Downstream services take the class as a dep, not the underlying store. Same pattern likely applies to `TokenStore` / `PluginStore` if a future service ever needs to mutate them — go through the wrapper, not the store.
- **Closure capturing `settings` directly snapshots the plugin's initial settings object — runtime toggles never propagate.** `this.logger = createLogger(() => settings.advanced.diagnostic_logging)` looks like it reads the live flag, but `settings` is a `const` from `await pluginStore.loadSettings()` at onload. When the user toggles `diagnostic_logging` in the settings UI, `pluginStore.saveSettings(merged)` writes a NEW object to disk; the closure still holds a reference to the original. Symptom: console output stays redacted forever, `fsm_transition`/`manifest_cache_invalidated` never appear, even with the flag visibly checked in Settings. Fix in `9fe02c5`: hoist the `cachedRef: { settings }` mutable container to right after `loadSettings()`, point the closure at `cachedRef.settings.advanced.diagnostic_logging`, and ensure every settings update re-assigns `cachedRef.settings = merged`. **Rule:** any closure that needs to read a "live" setting must dereference through the same mutable container the UI's update path mutates. If you can't see the assignment site that flips the value, the closure is reading a snapshot.
- **`vault.modify` / `vault.writeAtomic` from inside the plugin fires the SAME `modify` event Obsidian fires for user edits — `ChangeDetector` can't tell them apart.** Concrete: `RestoreOperations.writeRestore` calls `vault.writeAtomic` to put back an old version; Obsidian's vault watcher fires `modify`; `ChangeDetector.dispatch` enqueues it; the next FSM tick fires an inc that backs up the restored content as a "new change". Two ways out: (a) suppress at the source — temporarily skip `ChangeDetector` for the path being written (state machine in detector + restore handshake, complex); (b) absorb at the sink — let the inc fire, but with the inc-interval anchored on `earliest_pending_observed_at` instead of `last_commit_at` (commit `17453bb`), the user gets a 15-minute batch window where the restore "dust" gets folded into the next regular inc instead of triggering an immediate backup. Plus the no-actual-changes short-circuit in `runIncremental` (commit `8565463`) means a restore that brings the file back to a hash already in the chain produces no manifest. **Rule:** when a plugin component writes to the vault, assume `vault.on('modify', ...)` subscribers receive it. Either bypass the subscriber (advanced) or design downstream so a redundant event is harmless.
- **`Date.now()` collides at ms granularity inside tight per-file loops — batch ops must share one timestamp.** `RestoreOperations.buildCopyPath` produces `<base>.restored-<ISO-ts>.<ext>`; ISO has ms precision but a sequential loop over 50 files often runs entirely within a single millisecond. If each iteration calls its own `now()`, the rendered timestamps are identical → identical sibling filenames → `writeAtomic` of file N silently overwrites file N-1. Symptom is data loss masquerading as success: log says "50 files restored", disk has 1. Fix in `restoreDirectory` (commit `1847b86`): compute the shared `ts = this.now()` ONCE at loop start, then call a private `restoreAsCopyAt(path, snapId, sharedTs)` that threads it through `buildCopyPath(path, sharedTs)`. Single-file `restoreAsCopy` is unaffected — it still uses its own `now()`. **Rule:** any batch operation that produces "named-by-time" sibling outputs (restore-as-copy, snapshot dumps, log rotations) must share a per-batch timestamp. The default of "let each item pick its own time" is silently broken.

- **Test fixtures that fabricate `(fresh remote, populated local index)` silently violate a production invariant.** `tests/services/backup-service.test.ts` reconcile tests created a new `makeFakeDropbox()` while passing `initialIndex: primedIndex` so `getManifestPaths` only saw the new INC's manifest. Production never has that combination — a non-null `LocalIndex` always implies a corresponding `HEAD.json` on Dropbox, because the index is only persisted at commit step 6 (after HEAD has been written at step 5). The mismatch was invisible until a corruption-recovery probe (`runIncremental` → HEAD existence check) was added — then every reconcile test fell back to FULL instead of producing the expected INC manifest. Fix in `0625e13`: `makeHarness` auto-seeds `HEAD.json` on the fake Dropbox whenever `initialIndex` is provided. **Rule:** when a test fixture lets the caller compose pieces of system state independently, audit each combination against production invariants. If the fixture can express `(local=A, remote=B)` but production guarantees `A → B`, the fixture should enforce `A → B` by default and require an explicit override to break the invariant.

- **"Probe-then-recover" patterns must classify probe failures into three buckets, not two.** First version of the HEAD probe in `runIncremental` (commit `0625e13` first iteration) caught all errors and acted only on `PATH_NOT_FOUND`, swallowing the rest with the rationale "let the commit chain surface them later". That swallowed `AuthError(TOKEN_REVOKED)` from the integration test's `nextErrors` queue — the probe consumed it, the inc proceeded with no further error queued, and the AUTH_LOST banner never fired. **Rule:** in any probe-to-decide-recovery pattern, classify the probe failure into (a) the absence we're probing for → trigger recovery; (b) transient failures (network, 5xx, throttle) → re-throw, leave the probe-verified flag false so it gets re-tried; (c) permanent failures (auth, malformed) → re-throw. Never collapse (b) and (c) into "swallow everything else" — that wastes a recovery attempt that re-trips the same wall and hides real errors from the FSM.

- **Probe the data you're about to USE, not its presence-flag.** PR #9 probed `HEAD.json` to detect Dropbox-folder corruption. That caught the "user nuked the entire vault folder" case but missed Marcus's actual corruption: HEAD existed, the manifest it pointed at existed, but THAT manifest's `parent_id` referenced a deleted middle inc. `runIncremental` happily wrote yet another orphan inc whose `parent_id` pointed at the same broken chain top. Fix in `024f277`: probe the *parent manifest itself* — the snapshot we'd attach the next inc to (`last_inc_snapshot_id ?? last_full_snapshot_id`). PATH_NOT_FOUND there means the chain is broken at the top, regardless of where in the chain the actual gap is. **Rule:** when adding a corruption-detection probe, ask "what data does the next operation depend on existing?" — probe THAT, not a sentinel like `HEAD.json` that was correct yesterday but says nothing about today's chain integrity. Same shape applies to any next-step-depends-on-prior-state pattern (caches, snapshots, lock files, build outputs).

- **A reactive 429 gate alone does NOT prevent the storm — N parallel ops fire, all 429, all sleep the same `Retry-After`, all wake together and re-flood Dropbox.** First fix attempt (commit `808e347`) added a shared `rateLimitResumeAt` to `DropboxClient`: when any op observed 429, every later op would wait past that timestamp before its own SDK call. Logical, but useless against the actual failure mode — when `BackupService.uploadBlobs` runs `Promise.all` on a 4-element batch, all four ops are already in-flight before the first 429 surfaces. They each independently classify the 429, each independently sleep `Retry-After` via `retry.ts`, and each independently fire again at the same wake instant. Fix in `f5ab499`: add a proactive `TokenBucket` (default 8 req/s, 15 burst) at the head of every `attempt()` so the bursts never form in the first place. The reactive gate stays — it covers the case where another app on the same Dropbox account pushes the user over the limit unexpectedly. **Rule:** for SDK boundaries that face an external rate limit, always pair proactive throttling (token bucket / leaky bucket / semaphore) with reactive back-off. Reactive alone is structurally too late when callers issue parallel work. Sized the bucket conservatively under Dropbox's per-app `files/upload` budget (~10 req/s); raise via `DropboxClientOptions.rateLimit.requestsPerSecond` only if the user reports "backups too slow" without 429 noise.

- **Disabling an Obsidian plugin unmounts it but does NOT cancel in-flight Promise chains — retry loops keep running for up to ~60 s after disable.** Symptom that confused real-time debugging: user disabled Archivist in Settings → Community plugins, but the dev console kept emitting `POST /2/files/upload 429` for another minute. Looks like the plugin is still running — it isn't, but its `retry()` wrapper is. With `maxAttempts=5`, `baseMs=1000`, `capMs=60000`, and exponential backoff with full jitter, a single in-flight upload can keep retrying for ~31 s minimum, plus per-attempt `Retry-After` sleeps from 429 responses. Multiple in-flight uploads stack their tails. **Rule:** when "errors continue after disable" comes up in a bug report, ask whether the errors persist past 90 s. If they stop within that window, they're harmless residual retries from the unload moment. If they outlast 90 s, look for *another* plugin / Obsidian Sync / a second plugin instance. The plugin's `onunload` is not currently wired to abort in-flight retries — possible follow-up if this becomes a recurring confusion point: plumb an `AbortSignal` from `onunload` through `BackupService → DropboxClient.runOp → retry()`, which already accepts `RetryOptions.signal`.

- **Obsidian's `Notice` has no `.addButton()` API; if you need actions on a sticky notice, build a `DocumentFragment` with `createFragment()` and pass it to the constructor.** `Notice.addButton` only exists on `Setting`; `Notice` itself only exposes `messageEl` (since 1.8.7) and `noticeEl` (deprecated alias since 0.9.7). - **Any service that mutates `snapshot_index` must invalidate `ManifestCache`.** `ManifestCache` keeps an in-memory copy of the entire snapshot list and serves it to the Backup Browser view; writes that go through `SnapshotIndexStore.remove()` / `rebuild()` update Dropbox + the on-disk index but do NOT notify the in-process cache. Symptom in PR #61 verification: `RetentionService.runNow` deleted three manifests, logged `retention_pruned` per id, the on-Dropbox index was correct, but the Backup Browser kept showing all six snapshots through `_refreshSnapshots()` AND through full tab close-and-reopen — only an Obsidian restart fixed it. Fix (`fix(retention): invalidate ManifestCache after pruning`): add `invalidateManifestCache?: () => void` to `RetentionServiceDeps`, call it from `_runEvaluation` when `pruned.length > 0` (same condition as `triggerGcSweep`), wire a shared late-bound invalidator in `main.ts` that both RepairService and RetentionService point at. Pattern precedent: `RepairService` already had `invalidateManifestCache` in its deps and called it on every rebuild; the bug was RetentionService not following the same pattern. **Rule:** any new service that calls `snapshotIndexStore.remove` or `rebuild` must take an `invalidateManifestCache` dep and call it after a successful mutation. Grep for `snapshotIndexStore.remove\|snapshotIndexStore.rebuild` before merging a new service — if the caller doesn't also invalidate ManifestCache, the Backup Browser will go stale.
- **"No changes" incremental backups produce zero new snapshots, which can leave a tier bucket empty even after a "successful" backup.** When `runIncremental` short-circuits because the vault hash matches the previous snapshot (logged as `Inc backup: no changes`), no manifest is written and the snapshot list is unchanged. This interacts badly with aggressive tier configurations: `daily_days: 1` with no other tier enabled keeps the newest snapshot from "the last 1 calendar day". If today saw only no-change incs, today's daily bucket is empty; chain-integrity protects only ancestors of kept snapshots; with nothing kept, nothing is protected → ALL older snapshots become prunable. Observed during PR #61 retention testing on 2026-06-03: the day's 3 remaining snapshots (all from 2026-06-01) were auto-pruned after a no-change inc, leaving the user with zero backups. Mitigated by the new `always_keep_n` setting (PR #61) which protects the N most-recent snapshots regardless of tier rules, default 3. **Rule:** when discussing retention behavior with a user or designing new tier rules, remember that "we just ran a backup" does NOT imply "today's bucket is non-empty" — the bucket only fills when a real content change exists. The footgun + the safety floor are documented in issue #65 for user-facing operations docs.
